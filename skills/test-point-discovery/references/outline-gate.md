# 当前模块的大纲校验

首次调用就按当前任务逐模块实际运行固定程序。尚缺模块、资料或大纲时也提交已知字段，按返回缺口定位或澄清。一个模块的结果仅适用于本次请求列出的分支。收到阻断时可读资料、追问、展示大纲；聊天中不展示任何测试点正文，待评审文件也不创建、不追加、不改写。对其他模块分别运行同一入口。已有文件、规划完成、声称“已确认”均不足以出稿。

## 从实际答复登记采用依据

先读完整原消息、用户所指的原树或当时展示的版本，以及当前业务资料。用户明确要求按所给树编写时以 `adopt` 登记原树；用户对展示的版本作出实际肯定答复时以 `confirm` 登记。编号回答要逐项回查当时的问题。用户原文、附件选择、业务名称的等价性和节点归属由执行者逐项核实；确认的对象究竟是大纲、模块规划还是某条规则，取决于原问题和原意。举例、待考虑、沉默、助手推测、历史稿件和代理自拟验收指令不能登记为用户决定。

原树有“模块 → 至少一个具体业务分支”即可，按业务保留深度。逐项对照已知分支、层级与资料，有遗漏、歧义或需要增补则先展示整理后的版本，等待该版本的实际确认。已有决定仅恢复当时采用的树。取得决定后将其原样冻结，按当前拟写内容另建请求；不得从当前请求倒填旧决定。可在已有问答中记录决定文件及来源索引。输入、原话和程序请求保存在本机授权过程目录或临时目录。

## 起草与展示

1. 首次校验缺树或只有模块标题时，保留程序的阻断结果。回读当前模块的资料、已确认决定及排除范围。按资料列出实际入口、方式及其父分支，与输入树逐项对照。区分影响覆盖的业务方式与同一分支内的样本、步骤或措辞；后者无须为此扩展大纲。
2. 资料够用时直接起草树。用户说“例如”时，将例子作为组织线索。层级缩进可作两种解释时，资料能决定归属就据此整理；资料也无法决定时，指出有歧义的节点和两个具体归属，先等用户澄清。结构虽合格但漏掉资料明确的方式时，补到实际父节点并说明新增依据。已明确排除的方式维持原决定。
3. 对起草、整理、增删或移动过分支的树，用缩进列表展示模块和完整拟用层级，标明本次版本及相对原树的变化。用户能据此回答“采用这版”或指出修改位置。展示内容止于范围和问题，不夹入正文示例或预期。若用户要求修改，重新展示更新版。明确指定且层级清楚、资料核对完整的原树直接走 `adopt`。
4. 等待时，聊天止于上述树或范围澄清，待评审文件保持原状。保留这次展示的位置；下一轮先读完整上下文，核实用户实际在回答这版大纲。对其他问题的“确认”、原例、请求“先写文件”、助手自述与未回复均保持待确认。收到明确采用本版的真实答复后，以本次展示和该答复登记 `confirm`，用同一程序重新校验，再接既有阶段前提。

## 固定程序输入

从此 Skill 的目录运行 `python -X utf8 scripts/check_outline.py <request.json>`。只需 Python 标准库。请求为 UTF-8 JSON，例如：

```json
{"task":"借阅改版","module":"借阅","outline":{"module":"借阅","branches":[["登记"],["归还","柜台"]]},"scope":[["归还","柜台"]],"decision":"decision.json"}
```

`branches` 是从模块下一级到每个叶节点的有序路径，所有标签取自当前树。共同父节点可以重复出现在不同路径中。保留业务层级、顺序和名称；只有标题时传空数组。拟写的叶路径逐项放在 `scope` 中，编写全树时列全。尚无大纲或决定可省略相应字段。程序先检查模块和树，再核对决定。相对的决定文件路径以请求目录为准。

决定文件包含 `task`、当时的完整 `outline`、`kind`、`evidence`。每条证据由 `basis`（原树、展示内容或所答的原问题）和 `reply`（用户采用原话或对该版本的实际回答）组成。例如用户明确附树时两者可指向同一消息；先展示再答复时分别指向两个位置。原范围分布在多个问题或文件时分别登记。每个引用形如：

```json
{"path":"原问答.md","sha256":"原件字节的64位小写SHA-256","quote":"可唯一回查的连续原文"}
```

- 路径相对于决定文件，也可使用本机绝对路径。哈希在回查原件时计算。若来源会追加（如本地会话 JSONL），可加从 1 开始的 `line`，此时哈希只计算该行的原始字节，去掉行末 CR/LF。依赖章节标题辨别发言人时引用整份原问答。
- 支持原始 Codex JSONL 消息或带 `role/content` 的 JSON 消息列表，以及保存实际用户原话的 UTF-8 问答。Markdown 支持 `用户：原话`、`用户回复“原话”`、带“来源……用户回复”的同一节内 `实际回复：“原话”`，或有用户来源标注的“用户回复”节内逐项编号的原话。找不到来源时先定位实际消息；不得为通过程序编造或将助手文字重标为用户。保存会话摘录时保留实际消息来源和发言身份。
- 使用同一 JSON/JSONL 会话登记 `confirm` 时，程序核对助手展示在前、用户答复在后。引用完整可见的展示范围，回读答复全文及期间的修订，确认答复指向的具体版本。历史问答或分散在不同原件时，要从原问题、版本及答复出处核实对应关系；找不到对应关系则展示本版并等待。
- 原范围引用须能回查每个业务分支名称。沿用项目已经确定的同义名称时，可在决定中增加 `source_labels`，如 `{"现场归还":"柜台归还"}`，逐项核对原话指向相同业务。程序核对文字出处，执行者核对父子关系和原意。
- `request.json` 和 `decision.json` 是执行者根据实际资料制作的本地索引。历史用户可以用自然语言确认，无需回复程序格式或哈希。不要向公共工单、PR 或报告附原件、原话、路径或资料正文。

## 已采用范围的修订

修改已采用模块时，在请求内加 `previous_decision`，指向从当前问答恢复的最近有效决定文件。用新拟定的完整树作 `outline`；从本次实际要改的正文反推写入、删除的叶路径。还在征求意见的版本、上次的 `allow` 输出、旧稿上已有的标题均不能当作旧决定。即使只删旧稿或直接指定阶段 6，也要先过同一程序。

- `scope` 枚举本次要写入或细化的新树叶路径；仅删除时传 `[]`。另用 `remove_scope` 枚举本次要删除正文的**完整旧叶路径**，没有删除可省略。删除整支列出该支每个受影响旧叶，父标题若还承载保留的兄弟节点就保留。移动或改名时同时列出真正要新增和删除的路径。只收到局部反馈、某段省略时先核实意图，不能从差集推断用户要求删除。
- 程序回查旧决定的任务、模块、原树及用户依据，返回 `previous_version`、新版 `version` 和 `diff`。其中 `added/removed/unchanged` 分别列出新增、移除及仍在的完整叶路径。把新完整树及程序返回的 `review_text` 原样展示给用户，它标明新旧版和具体增删；在取得本次展示后的明确答复前，两个渠道都保留受影响正文的原状。
- 只继续仍在的分支时，另发局部请求，仅在 `scope` 中列这些叶路径，无须提供新决定。细化同一叶下检查的样本条件、表述或可观察预期，保持原树与原叶路径；核实业务依据后按原决定继续。如果条件实际上引入另一业务方式，先更新大纲。旧决定授权时，`decision_version` 指向旧版，`scope` 为本次实际放行的范围。
- 用户确认本次展示后，新建 `confirm` 决定，`basis.quote` 须含当时完整的 `review_text`，并按上述引用规则保留完整拟用树与实际答复。用原 `previous_decision` 加新版 `decision` 重新运行；只提交要改的新增叶及要删的旧叶。复核程序返回的 `scope/remove_scope` 与即将执行的编辑逐项一致，再按本次放行的路径修改。仍有效部分可另行接续。修订记录应保留两个版本、两个决定及此次差异，后续从已确认的最新决定接续。
- 移除最后的全部分支时，完整新树的 `branches` 与 `scope` 均为空，`remove_scope` 列实际待删旧叶。仅此次取得明确答复后的删除可以执行；没有具体分支的模块不能开始写稿。

例如旧树的“柜台 → 归还”移动到“自助 → 归还”，请求列 `"scope":[["自助","归还"]],"remove_scope":[["柜台","归还"]]`；只细化保留的“登记”时，单列 `"scope":[["登记"]]`。批准范围与阶段 7 的具体稿评审仍分别留存。

## 放行与阻断

只有进程返回 0，输出单个 JSON 的 `status` 为 `allow`，且 `task/module/scope/version` 和当前大纲、决定匹配时，才可将本次结果用于该模块。保存返回的大纲 `version` 与 `decision_sha256`，便于复查本次到底依据了哪份输入。程序只读，具体写稿仍须现有阶段 3 规划、阶段 5 来源及问题处置复核等前提成立。

非零退出、程序不可调用、文件不可读、输出缺失或无法关联当前范围，都停在写稿前。说明该模块和具体原因，保留原稿；可补充来源、澄清业务或展示待确认大纲。聊天和文件共用这次判断。这里观察的是 Skill 的正式工作流；宿主全局输出或任意文件写入拦截属于独立的运行时能力。
