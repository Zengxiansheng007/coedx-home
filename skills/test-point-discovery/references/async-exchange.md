# 数据交换与异步处理

新规划先按[规划前业务理解](planning-confirmation.md#规划前业务理解)厘清主要操作与关联，实际询问影响划分的问题，再提出模块表图。整体阶段的明确规则仅记为分析依据，尚不形成测试点稿；已有确认规划的接续沿用其范围与顺序。

导入、同步、通知或后台任务资料到达时读取。它是项目组织方案，不是官方测试技术分类；不依赖业务系统或外部模型，不实际提交文件、通知、重试或生成测试数据。

## 识别与组织

实际读 PRD 和用户说明，识别任务、交换对象、来源和目标、字段及对象标识，区分任务编号与业务对象编号。说明推荐理由：受理后仍有过程或最终数据结果时，以“任务/交换对象 → 输入受理 → 过程 → 最终结果及数据对应”为主线；即时操作占主导时只作补充视角，不把所有操作都改为异步。

给出实际模块范围、顺序、已知关联与未知影响，交用户确认。新规划继续入口绘图步骤；接续已有确认范围只核对展示版本、答复和范围，不重复绘图。新增关联只建议，不自行扩大范围。

## 澄清与具体检查

先复用入口的模块澄清，按依赖分轮提问，独立问题同轮提供假设例子、可自定义选项、推荐理由与代价。部分答复只明确实际对象、条件与行为，剩余继续追问。以下是核对方向，只有实际能力才形成确定检查：

- 输入与受理：文件/事件/消息或其他真实输入；已知必填、格式和拒绝条件；受理提示、任务编号及其含义。受理只说明进入处理，不等于目标落地或收件人收到。
- 过程：实际可见状态、状态对应的同一任务、变化触发条件和可观察内容；缺失状态、时限或生效时点先问。不额外添加排队或轮询接口。
- 最终结果：成功、部分成功、失败是否存在、各自判定条件、正确行保留或回滚、成功/失败计数、错误明细和原因。未知部分成功规则时，不自行写“8条成功2条失败”。
- 数据对应：源字段→目标字段；同一对象用什么标识对应；任务→本批对象→源行/失败明细怎样关联。核对值及对象，不能只核数量。通知场景区分提交、渠道受理与实际业务定义的送达/阅读，结果无证据不声称送达。
- 实际能力：逐项核对重复输入、重试、超时、取消、幂等是否支持及规则。能力未知先问“是否存在”；存在后再问触发条件、作用范围、次数/时限、结果和对既有对象影响。未知不等于支持，也不等于不支持。不从外部产品借默认次数、协议、重试间隔或回滚保证。

上述阶段按每项操作本轮已定终点取舍，先复用明确结果，仅询问未明且影响范围的终点。送审若止于审核端收到同一任务，就核对其任务标识、必要状态和提交数据。后续审批、发布或渠道送达按各自范围决定处理。取消若已明确业务效果，直接写对应任务或输入受何影响。逐项结果写法见[编写约定](writing-review.md)。

对实际状态，用状态、事件、条件、结果梳理可见变化，未知触发/终态保留问题；不宣称已覆盖完整状态转换方法。对输入按资料证明的相同处理依据分组，例如格式通过/未通过；分类依据、有效规则缺失时先问，不根据字段名称猜手机号长度。已集成专门方法时可按需使用，不能硬引用尚不存在的参考。

读取[错误推测与检查表](method-error-guessing-checklist.md)补候选遗漏，按[输入判定](module-clarification.md)区分直接推导检查与额外风险。额外风险说明价值、成本与选择后交用户决定；纳入后未知预期继续实际提问，只有明确暂留后才进产品区。拒绝的建议记录范围理由，在适用项目中沿用，未采纳不进正文。

## 自检与评审

逐条对照原始资料、用户关切和答复，核对受理/过程/终局、任务/对象身份、源目标字段和结果依据都有检查或明确去向。按[共用范围与差异](writing-review.md)单写模块内相同规则并标明适用功能，各功能的阶段、条件、对象对应与结果差异仍可恢复。未知以问题编号定位，顶部集中明确暂留产品问题。只写需要检查什么，完整用例和执行留在下游。

按入口编写约定形成待评审副本；问答结束仍不创建准确基线。具体评审通过后读取评审更新约定，更新同一路径准确 MD，在同文“资料与Agent交接说明”记录来源条目对应、场景纳入与规则明确的区别、评审版本和未决影响。有未决时由用户决定继续范围，不默认进入下一模块或交接。

依据：已确认方法设计v0.3“数据交换与异步处理”；[Microsoft Azure Asynchronous Request-Reply](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply)（核读2026-11-07，Solution）：仅作受理与最终完成区分的架构实例，不规定本项目协议或能力。
