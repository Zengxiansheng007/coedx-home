# 模块测试点梳理

## 当前能力与边界

本版交付 TPD-01A/01B/01C/01D：读取可访问的看板 PRD 和用户说明，形成候选模块规划，实际调用 archify 将表图一起交用户确认，按已确认范围澄清当前模块，编写并自检局部待评审测试点。资料理解和关联判断由执行 Agent 完成，无语义分类脚本、外部模型或业务系统依赖。仅在授权的输出位置写过程材料；否则直接在回复中提供。

本版同时交付 TPD-01E/02/07/08：具体测试点评审后的同一准确 MD 更新、模块推进、聊天/局部MD/受支持XMind反馈的影响重审，以及按实际依赖建议并由用户决定范围的单文件文档交接。局部待评审文件和历史过程材料保持原身份，具体评审通过后才有准确基线。XMind 导入与编辑往返按实际客户端验证，未执行时明确未验证。只梳理测试点，不生成完整用例、不运行真实业务、不宣称 P0 通过或自动启动 P1/P2。

采购、审批等跨模块业务或对象生命周期资料先读取[流程与生命周期](references/workflow-lifecycle.md)，据实际内容选择主线，复用以下规划、澄清、评审及反馈步骤；本分支支持先流程后模块、状态/事件检查与模块新事实回流重审。七类参考接通不代表全部规格验收已完成，按实际证据报告范围。

TPD-03 扩展信息维护与规则计算，TPD-06 扩展数据交换与异步处理，复用相同规划、澄清、编写、自检和具体评审后更新流程。七类是项目组织方案，不是官方测试技术分类；方法参考按需读取，不为每种方法建独立 Skill。

## 执行顺序

用户功能、数据或价格随角色/会员权益变化时，先读取[角色与用户权益](references/roles-entitlements.md)，贯穿下列分析、组织、自检及反馈步骤。TPD-05增加逐用户完整分支、四类条件区分及权益变化重审；默认模块→用户类型→功能/规则，替代目录须用户决定。

1. **核对输入。** 实际读取用户指定的 PRD 和文字说明，记录文件/链接、标题或条目位置及可见版本。读取失败时指出具体来源并请用户提供可读内容，保留已读资料但暂停依赖缺失来源的规划。没有 PRD 时只说明本版保留将来无 PRD 入口，请提供可读 PRD；不以一句想法补造业务方案。超出现有参考与输入能力的请求说明实际边界，不以参考接通作为验收证明。
2. **逐条理解。** 看板读取[看板资料分析](references/dashboard-intake.md)；维护记录的实际操作读取[信息维护](references/information-maintenance.md)；条件、金额或公式决定结果时读取[规则计算](references/rule-calculation.md)；跨模块接力或状态变化读取上方流程/生命周期参考，识别对象、参与者、事件、条件、传递与生效，不套图表模板；导入、同步、通知或后台任务读取[数据交换与异步处理](references/async-exchange.md)，澄清、编写和自检时返回该参考核对受理/过程/最终结果及数据对应，实际状态与输入分类只作适用补充。混合资料读取所需参考，按实际内容理解而非关键词分类。识别对象、操作、规则、关联、用户关切和缺口；分组保持分析建议身份。
3. **提出候选安排。** 给出本轮范围、明确排除、推荐顺序和组织主线理由。看板从模块→图表/指标起步，信息维护从模块→实际操作起步，规则计算从规则→条件分支起步；跨模块接力先流程后模块，生命周期从对象→状态/事件起步；异步从任务/交换对象→输入受理、过程、最终结果及数据对应起步。解释主线、补充视角及裁剪理由，由用户确认实际组织与范围；不机械补齐操作/状态/角色或全部组合。用户明确范围沿用其实际说明；新增关联与风险只提建议，保留待确认。
4. **整理关联。** 用与范围表相同的端点名或编号，写明每条关联的方向、触发条件、传递内容、资料依据及未知影响。区分已记载关系、Agent 推断和待确认关系；没有依据的箭头不补造。有跨模块流程线索时建议范围并解释原因，不自行纳入或开始流程测试点编写。
5. **绘图并一起确认。** 按参考中的自检核对候选表和“资料与Agent交接说明”，再读取[规划绘图与确认](references/planning-confirmation.md)。直接调用实际 archify 生成 HTML 和图片并读图，简表与图一起呈现，不新增单独的表格批准轮。按真实反馈同步修订范围、顺序和表图，保存真实答复；推荐、沉默和模拟回答均不算真实确认。
6. **澄清当前范围。** 规划未确认时等待。确认后读取[模块分轮澄清](references/module-clarification.md)，先核对当前范围的资料与已有答复，再集中问前提明确的独立问题；依赖问题等前置答复后继续。已有规划的接续请求直接核对展示版本、答复及范围，不重复绘图或批准。纳入跨模块流程时先澄清、编写、自检并评审具体流程，通过后按决定范围进入模块；生命周期按实际状态/事件与允许动作处理，按实际证据报告支持及未验证范围。
7. **交付可用结论与未决影响。** 保存问题、实际答复及其范围；未答、推荐和冲突分别保留。存在未决项时请用户决定可继续范围，沿用已有具体决定，不要求批准长篇业务需求。仅要求澄清结果时停在该阶段；问答结束不是具体测试点评审通过。
8. **编写并自检待评审测试点。** 请求进入编写且范围已决定时，读取[编写、自检与待评审文件](references/writing-review.md)。从原始资料和实际答复形成具体检查，每个图表/功能分支独立完整；集中问题、核对来源与遗漏，输出有范围的局部待评审 MD。交具体测试点供用户评审，等待其反馈，不进入下一模块或创建准确基线。接续已完成规划和澄清时核对已有证据即可，不重复绘图或增加批准轮。

9. **承接具体评审并推进。** 收到当前待评审内容的反馈时，读取[评审、准确文件与模块推进](references/review-and-progress.md)。未通过回当前模块修订，呈现完整受影响分支重新评审；具体内容通过后才创建或更新同一准确 MD 和版本。保留其他模块、来源、有效确认及未决状态，再按已决定的顺序与继续范围回到下一模块的澄清步骤；没有后续决定时停在本轮完成状态。规划或答疑不构成测试点评审。

10. **核对聊天与MD修改。** 收到已评审内容的修改、编辑后的局部MD或跨分支影响时，读取[反馈与影响重审](references/feedback-review.md)。固定原范围、基线和反馈来源，形成候选；删除歧义先问。展示业务摘要与完整受影响分支，沿用不受影响结论，再回评审步骤更新同一路径。接续反馈直接走本步，无需重做规划。

11. **接收XMind回传。** 收到原生XMind反馈时，读取[XMind读取与同一评审](references/xmind-feedback.md)，实际运行只读helper并读回传的有序主题和来源身份；固定原范围及现行准确版本，由Agent核对文字、层级和影响，再走同一候选/具体评审/同MD更新。未支持格式、歧义删除及无法对应先核实；不以格式成功代替业务确认。

12. **按决定交接。** 请求交接或先交明确部分时读取[单文件交接](references/single-file-handoff.md)。核对最新准确 MD 及来源，按实际跨分支依赖提出交接与保留建议；分别记录场景纳入和规则明确，等待用户选择。将实际决定、依赖、范围与下游边界更新在同文说明区，回读保真。接续交接直接走本步，不重开规划；没有准确基线则先完成具体评审。文档交接不表示下游程序直导或 P0 已通过。

## 完成判定

交接分支使用 `tests/test-point-discovery/handoff-request.md` 实走局部未决及等待/拒绝/部分选择，按对应 rubric 核对；最终由独立接收者仅凭最新准确 MD 与其引用恢复范围、检查、来源、实际决定、未决依赖及下游边界。未执行恢复验证就明确未验证。

XMind反馈开发验证使用 `tests/test-point-discovery/xmind-request.md`；三入口同MD链见 `xmind-run/conversation.md`，真实原生往返另绑定客户端观察及文件hash。只读格式成功不能替代具体评审，历史副本保持过程身份。

流程/生命周期分支以 `tests/test-point-discovery/workflow-lifecycle-request.md` 和对应 rubric 核对真实入口的逐轮输出、实际图像、流程先评审、限定继续及#70受影响完整分支重审。方法参考不代替具体测试点，模拟答复不冒充真实业务确认。

异步分支开发验证使用 `tests/test-point-discovery/async-request.md`，逐轮记录在 `async-session.md`；只验证明确标注的模拟范围，图形前提和客户端未验证项单列。

评审更新分支还须核对准确文件路径、实际展示版本与评审范围；拒绝保持待评审，批准只更新批准内容，局部省略保留，未决与历史决定可从同文说明区恢复。开发验证使用 `tests/test-point-discovery/progress-request.md` 实走两模块及拒绝修订；实际使用仍等待真实用户决定。

反馈分支使用 `tests/test-point-discovery/feedback-request.md`；核对候选未提前更新准确文件、遗漏与删除区分、完整关联分支、实际评审和同文件来源历史。自检发现未涵盖影响时先补候选重新评审。

候选规划须可从来源核对实际内容，用户说明均有去向，顺序和主线有理由，关系方向/传递内容/未知影响清楚。澄清结果须区分实际答复、未答、建议和冲突，说明对当前模块的影响及用户决定的继续范围。待评审文件须经来源、适用维度和关联影响自检，每个分支独立可读，两类问题在顶部、来源映射在同文说明区，范围与待评审状态清楚。风险与未知规则保持原属性。未满足时修正本阶段材料；源资料不足时明确缺口和影响。

开发者验证本入口时使用仓库 `tests/test-point-discovery/requests.md`，澄清分支使用 `tests/test-point-discovery/clarification-requests.md`，编写分支使用 `tests/test-point-discovery/writing-request.md`，由独立评审者核对实际输出。经明确授权的开发模拟可用逐轮实际发送的模拟回答验证交互，每轮保留展示版本、回答原文、模拟来源、适用范围及未决状态；只代表限定模拟行为，实际使用仍由真实用户确认。结构通过只证明入口可读取；行为未执行时明确写“未验证”，不能预填验收结果。

信息维护/计算接续验证使用 `tests/test-point-discovery/maintenance-calculation-request.md`；核对实际原始资料、适用判断、未知项提问、方法形成的具体检查及评审后同一 MD。其模拟规划前提不证明新规划表图或实际业务已验收。

用户权益接续使用 `tests/test-point-discovery/roles-request.md`：核对独立完整用户分支、未知规则、目录决定及权益变更的完整影响重审与同MD更新；执行者自检与Root独立审查分开，模拟不证明真实业务。接续规划前提不证明新表图或客户端兼容。
