# 从材料形成可评审的专业用例

首次生成、扩展、反馈、恢复及公共定义变更后都应用本流程。使用既有候选、覆盖记录
与唯一问答，不增加专业判断包或另一份答案台账。此处指导编写判断，不是语义分类器
或已通过证明；具体稿仍需按当前版本评审。

## 1. 重新读材料，再确定当前范围

读完整输入、必要依赖、原问答中的有效答复、已确认范围及适用版本。区分来源事实、
实际观察、用户决定、编写建议和未决规则；模拟材料及答复始终标模拟。对已有答复
核对依据是否变化，只问会改变本轮操作、数据或结果的剩余问题。

完整重新生成从上述材料形成新的解释、候选和数据关联；旧候选用于身份匹配与差异
对照，旧稿用于比较。来源的章节、脚本动作或官方示例都是待解释的材料，不直接
充当最终用例。保留原文件、原P0、历史证据和旧评审；在独立输出中保存新版本。

本步完成：本批来源、版本、可复用决定及仍受阻范围可在现有任务记录定位。

## 2. 先确定业务路径与每例目标

从完整流程识别业务对象、角色、初态、触发、状态变化及检查终点，再提出真实业务
分组供评审。同功能的P0/P1/P2沿其实际功能路径组织，分级和生成阶段不是功能目录。
保留产品/系统/模块各层语义；`business_group.path` 只承载实际分组，不再次包裹
`module_path` 已表达的同一层。不同语义层同名时仍保留。分组依据写入
`business_group.source`，纯重组保持原身份、数据和覆盖。

用业务中文写标题、动作、条件及结果；界面标签、原始输入、配置引用和专有名称按
实际来源保留。中文说明解释具体触发和结果，不能只将英文来源整段搬进中文标题下。
简单数据按现有表达契约写“对象名：值”；复杂约束、空串及首尾空格等关键差异可辨，
实际 `value`、`id`、`data_refs` 不因翻译或展示而变化。

本步完成：每例有可从来源说明的目标和终点；已有同目标按
[目标准备归属](goal-preparation.md)处理，不为迁移检查而重复建例。

## 3. 逐动作确定归属，再形成完整序列

按[目标准备归属](goal-preparation.md)逐动作核对所建立状态和后续消费者，再按
[源语义](source-semantics.md)编写操作、数据、预期与观察。先写完整目标序列，之后
才判断公共操作提取和P0整步复用；公共定义的范围、例外及执行频次依
[聚合契约](aggregation-contract.md)，整步等价依[复用契约](step-reuse.md)。

每个准备动作须使当前目标可执行，且有就绪结果；就绪不是目标通过。按目的切分，
不按统一的前N步、相同点击数或全批模板切分。目标本身就是某操作的检查时，该操作
留在测试步骤。只为特定目标服务的测量保留在真实消费者处；依赖本次值的用例取得
本次适用值，定义复用不改变实例有效期。公共前后置在模块直属层；单例只呈现实际
特殊项，没有来源义务的后置不生成。

本步完成：从初态到终点的全部动作、数据及独立结果可按顺序还原，局部不适用仅阻塞
受影响内容，实际例外不被特殊项偷偷覆盖。

## 4. 先分解独立观察方面，再声称覆盖

从原测试点及其必要来源逐项识别可单独失败的结果，写成可观察的检查方面：说明
检查对象、触发/时机及结果。一次操作有多个独立结果时，各方面分别可定位；同义
预期与验证点只表达一次，具有不同对象、条件、触发、时机或结果时保留差异。

例如合成订单的“提交有效订单”可分别观察“订单进入待支付”和“库存按数量占用”。
只写前者时，后者仍是具体缺口；不能由“全部预期正确”或同一个全包方面表示两者
已覆盖。这个例子不规定任何真实产品行为，也不强制每例恰好两个方面。

先确定 `manual_points.checks.aspects`，再把当前完整用例中实际承载的方面填入
`coverage.links`。关联表能证明所填方面之间的关系，不能证明方面完整或业务成立。
核对原文中的条件、数据和独立结果均有落点；部分覆盖写具体缺项及其影响，延期/
排除沿原机制保留实际决定。不同边界输入独立成例；额外组合保持建议身份及用户选择。

本步完成：每个要求的方面能定位到对应操作、数据、预期和可观察验证；未覆盖部分
明确，不能把材料中没落到用例的结果自动计为已覆盖。

## 5. 逐例解释分级

保留仍适用的已确认等级；为每例核对 `priority_basis` 和 `priority_factors`：重要性
说明该目标承担的业务能力，风险说明该条件下的具体错误及影响，频次说明实际触发
场景及来源或明确的推断。相同等级可合理重复，但理由须能解释本例与相邻场景的
差异。缺少使用统计时写有依据的定性判断和不确定性，不编造数值或默认“其余常见”。

例如合成订单的库存扣减错误可能造成超售；历史订单排序错误可能影响查询定位。
两者即使同级，也需各自的失败影响及触发说明。不能把共同的“数据正确性/常见”
复制为逐例分析。已确认等级无需重问；实质变化才回原问答处理相应决定，历史不改写。

本步完成：每例等级、具体三因素及当前决定依据一致；建议与已确认决定身份清楚。

## 6. 完整还原后保存与交付

读本批及必要依赖，内部还原完整操作、数据、预期、断言及终点，再经实际公开入口
生成并保存。依[聊天交付](chat-delivery.md)交付同版范围副本，直接邀请评审具体稿。
必要来源和技术约束保留在既有权威资料或模块Agent说明，不变成额外业务步骤、复制
问答或第二答案权威；关键业务条件仍留正文。缺失/失效引用暂停其实际依赖范围。

回读候选与实际文件，逐例比较目标、路径、顺序、数据原值、范围例外及独立结果。
反馈与恢复沿同一流程核对受影响内容，保留未变决定及未展示用例。结构/API检查仅
证明输入完整性、映射和保留；另由无预期成稿提示的实际生成及独立REQ/AC审阅判断
专业质量。生成、具体稿评审、客户端导入与真实业务执行分别报告。

## 规则解释与实际来源

规则答复的 interpretation 归纳实际规则或决定的含义；复用旧答复、是否重新提问等
过程写回原唯一 QA 的 note/qa_ref。选级和风险依据按实际用途在标题或既有模块 Agent
说明定位，不冒充产品行为规则。已有历史文本按当前来源逐叶评估，未知业务解释保留。

分别核对动作框架、具体数据以及具名预期/观察各自的实际依据；所引范围须实质支持
对应内容，不能把整步或整节标题来源盲套所有 claim。已知来源准确引用，无依据者
明确待核，不冒充材料事实。
