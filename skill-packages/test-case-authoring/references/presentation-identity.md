# Chinese presentation and stable identity

Read before display, rename, same-name feedback or a Markdown/native return.

Author a Chinese business title from the supplied meaning; never prefix it with
the stable English case ID. Preserve priority, business actions, data and checks.
`render_batch` and `render_review_batch` project one candidate version. Public
trees omit English identity headings and use business names in references.
The internal flat renderer is source mapping only, never a user deliverable.

Keep each original case ID on rename; keep same-name cases as separate records.
References and the initial review baseline retain stable IDs. A title alone or
node order is not identity evidence. Inspect business path, role, state and source
relation. Explain ambiguity in business terms and wait for the actual answer;
record it in the existing Q&A log. If two returned subtrees are indistinguishable,
ask which business difference distinguishes them; use clarified chat changes
against the existing IDs and regenerate instead of creating duplicate cases.

For chat, translate the clarified change into existing `changes` entries with
stable `id`. For a later revision supply `source_version` and `before`. Actual
reply, summary confirmation and final review remain required. The agent maintains
these technical fields; the user reviews business content.

For Markdown, `aggregation.feedback_topics(markdown)` returns observed titles,
paths and complete subtree digests without guessing source IDs. After actual
business clarification or an existing explicit source mapping, the agent supplies
`case_bindings={case_id: {returned_digest, source_version, actual_reply}}` to
`prepare_feedback`. Use the displayed return's version and preserve the actual
identity answer verbatim. Unique complete unedited subtrees can match themselves.
Changed or identical subtrees without unambiguous binding raise `ValueError` and
return to clarification. Matching never uses Chinese title or ordinal alone.
Paths and applicability are generated structure: clarify their changes. Shared
preparation edits still propose changes for every owner.
Historical generated English-ID headings remain valid explicit identity at the
exact baseline version and module path. New rendering never reproduces them.

For native XMind, `inspect_xmind_feedback(path)` exposes Markdown/topics for agent
inspection; pass clarified `case_bindings` to `prepare_xmind_feedback` or
`--case-bindings <internal-json>`. Support remains one `content.json` sheet with
attached plain topics. Unsupported annotations, legacy XML, structural ambiguity
or absent identity evidence remain pending. Native topic IDs have no registered
import baseline and do not establish case identity. No arbitrary client support.

Bindings remain internal proposal evidence and feedback history. They do not
authorize application, final review, merging or execution. Scope copies exclude
unseen cases without deleting them. Regenerate both views after agreed changes
and review the exact new version. Keep full catalog and dependency identities;
merge only through the existing approved scope boundary. PRE-04 owns changes to
human-view file emission policy.

Verify Chinese titles and hierarchy in the actual agreed XMind client. Static
and synthetic native checks do not establish client or business acceptance.
